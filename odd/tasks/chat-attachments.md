# chat-attachments — document and image attachments in the Assistant chat

Branch: `feat/chat-attachments` (base `origin/master` @ 7d85766c). Delivery: `ask-on-risk`.
Test runners: `pytest` from `src/tools/demiurgos-suite`; `cd frontend && npm test`.

## Specs

### T1 — Document attachments (docx + pdf)

**S1 — Attach control.** The Assistant composer exposes one attach action that accepts `.docx` and `.pdf`. A chosen file uploads to the server; a chip shows the file name and its extracted character count; a remove action discards it. The attach action is disabled while a turn is in flight.

**S2 — Upload endpoint.** `POST /api/{mundo}/ai/attachments` accepts multipart `file`, validates the extension and a 15 MB size cap, extracts the text server-side, stores it for 4 hours (at most 32 stored attachments; oldest evicted first), and returns `{id, name, kind, chars, truncated}`. Rejections are structured with a stable machine code and HTTP status: `attachment.unsupported_type` (422), `attachment.too_large` (413), `attachment.too_many` (422), `attachment.empty` (422), `attachment.conversion_unavailable` (422), `attachment.conversion_failed` (422). Codes follow the repository's dotted registry convention (`world.not_found`, `import.job_not_found`).

**S3 — Failure is safe.** Extraction and dependency failures never crash the server and never kill a request. A rejected upload stores nothing and leaves the chat state unchanged.

**S4 — Prompt context.** Each send carries the conversation's `attachment_ids`. The server injects the extracted text into the activity run prompt in a delimited block, capped at 30,000 characters per attachment, and marks truncation. The semantic classifier gate receives only attachment metadata (names and kinds), never document text.

**S5 — Grounded answer.** On the activity surface the assistant answers using the attached content. When a question refers to an attachment, it must not invent content that is not in the attachment.

**S6 — Default prompt.** Sending with an attachment and no typed text uses the localized default prompt: `Resume el documento adjunto.` / `Summarize the attached document.`

**S7 — Attachment lifetime.** Attachments belong to the conversation and are re-sent on every turn until removed. An unknown or expired id returns `attachment.expired` (409); the frontend drops the stale chips and shows a localized notice without sending.

**S8 — Memory hygiene.** Document text is never written to conversation memory or distilled summaries; only attachment names are recorded.

**S9 — Scope.** Works for the world-scoped Assistant and the global (Taller de Ideas) Assistant.

**S10 — PDF dependency.** The optional dependency set ships markitdown's PDF extra so `.pdf` conversion works where the optional install succeeds; where it does not, the `attachment.conversion_unavailable` degradation applies.

### T2 — Image attachments (vision)

**S11 — Image attach control.** The same attach action accepts `.png`, `.jpg`, `.jpeg`, `.webp`, and `.gif` in addition to `.docx`/`.pdf`. The chip shows the image name and the character count of its generated description. Images count toward the same five-per-turn cap.

**S12 — Server-side vision.** On upload, the server generates a JPEG thumbnail (max 300px, aspect preserved) and asks the product's validated vision provider for a detailed description in Spanish: what is visible, people/objects/places, colors, composition, style, atmosphere, and a transcription of all visible text. The description is stored as the attachment text (same 30,000-character cap and truncation marker). The image bytes never reach Hermes: the run prompt receives the description under a label that says it was generated by vision.

**S13 — Vision availability.** If the active assistant model is not proven multimodal, the upload is rejected with `attachment.vision_unavailable` (422) and localized copy; nothing is stored. A provider failure or timeout rejects with `attachment.vision_failed` (502); nothing is stored. A file PIL cannot decode is `attachment.unsupported_type` (422).

**S14 — Capability truth.** A stored `capability` of `unknown` is not proof of anything: the assistant catalog may supply the capability, and a product-recorded causal vision acceptance for the current config revision proves `multimodal`. `deepseek-flash` is catalogued as `multimodal` (label `DeepSeek-V4.1-Flash`), matching the model the causal vision probe accepted. A save whose text and vision probes pass persists `capability: multimodal` (the probe is the proof). The importer's existing gate is unchanged: without explicit acceptance evidence, a stored `unknown` still skips vision.

**S15 — Fixed description.** The description is generated once at upload; follow-up turns reuse it. There is no per-question re-analysis and no OCR beyond what the vision model transcribes into the description.

**S16 — Bounded bytes surface.** The original image bytes are never stored or served back. A generated JPEG thumbnail (max 300px on the longest side) is kept in memory alongside the description and served only through the attachment's thumbnail route (S17).

**S17 — Preview before sending.** Each composer chip previews what was attached: an image chip shows the generated thumbnail (fetched from the attachment route), and a document chip shows its type badge (`docx`/`pdf`). If the thumbnail cannot load, the chip falls back to the type icon without breaking the chip or the send. The thumbnail route is scoped to the same world/global context as the upload and returns no-store bytes; an unknown or expired id answers 404.

### Assumptions (not requested verbatim; Owner may overturn)

- A1: T1 covers text extraction only (`.docx`, `.pdf`).
- A2: Limits — 15 MB per file, 30,000 injected characters per attachment, 4 h TTL, 32 stored attachments, at most 5 attachments per turn.
- A3: Multiple attachments per conversation are allowed.
- A4: T2 analyzes each image once at upload (S15) instead of per-question re-analysis; cheaper and deterministic.
- A5: The same 15 MB file cap applies to images.
- A6: The generated description is Spanish (product default), independent of the conversation language.

### Out of scope

- Drag-and-drop upload.
- Persisting attachment bytes or text across a server restart.
- OCR for scanned PDFs.
- Per-question vision re-analysis.
